# SpecFuse 设计手记（2026-08-27 版）

> 这是设计手记的第二版。第一版（[2026-06-24](./design-philosophy-2026-06-24.md)）写下的思考方式大多仍然成立，但结论已经过时了一部分——最显著的是流水线拍序：第一版的 **Think → Grill → Do → Verify** 已演进为 **Think → Do → FuseReview → Verify**。本版如实记录演进，包括一次完整的"加拍又删拍"过程。方法论的一个好处是：它自身的变更也走它自己的流程。

---

## 一、意图：我们到底在解决什么问题

### 问题不是 AI 写不好代码

"AI 能不能写代码"早已不是问题。真正的问题是：**AI 的产出质量不稳定，而且你无法预测它什么时候会出问题。**

同一个 AI，同样的指令，今天写出来是 TDD 全覆盖的干净代码，明天就可能跳过测试、遗漏边界、声称"已完成"但实际没跑过一次测试。这不是能力问题，是一致性问题。

### 痛点的本质：信任缺口

开发者和 AI 之间存在一个**信任缺口**：

- AI 说"done"，你不敢直接 merge
- AI 说"测试通过"，你不确定它真的跑了
- AI 在第 3 个任务时表现完美，到第 7 个任务开始犯低级错误——但它不会告诉你

**SpecFuse 的意图就是填补这个信任缺口：让你在合理成本下，相信 AI 的产出是可靠的。** 不是靠"更好的 AI"，而是靠流程约束：你不需要每次都亲自验证 AI 有没有跑测试，因为规则让它不跑测试就无法标记完成。

### 实践中暴露的第五个痛点：证据本身可以是空的

前四个痛点（完成声明不可信、大变更后半段塌方、方向性错误、决策不可追溯）在第一版已有论述。流水线运行一段时间后，暴露出第五个更隐蔽的痛点：

**测试存在且全绿，不代表测试证明了任何东西。**

断言可以复述实现（`expect(result).toBe(fn(x))` 式的同义反复）、可以永真、可以只测外壳不测输入生效。TDD 铁律保证了"测试存在 + 测试通过"，但**保证不了"测试在目标回归上真的会失败"**。这类"绿但是错"的代码能通过流水线上所有既有闸门——因为所有闸门都信任绿色测试。

这个痛点直接催生了 FuseReview 拍（见第五节）。

## 二、思考过程：从痛点到设计原则

第一版记录的五个思考转折点（约束过程而非产物、流水线而非组合、声明式规则、规则分级、成本自适应）全部保留——它们仍是这套系统的地基。此后新增了三个转折点。

### 转折 6：评审的位置从"实施前拷问"移到"实施后冷读"

第一版在 Think 和 Do 之间放了 Grill——一个实施前的设计拷问环节。它的理论价值清晰：设计缺陷在代码未写时修复成本最低。但实践给出的反馈是：**流程太重**。

一问一答的审查协议、备份回滚机制、9 问软上限、双向一致性扫描——对大变更有价值，对多数变更是过度开销。更关键的是，实施前审查能抓的问题（方向错误、边界不清）大部分已经被 brainstorming 的方案对比和逐制品审阅覆盖了，Grill 的独特增量价值小于它的固定成本。

与此同时，第五个痛点（空证据）指向的是一个**实施后**的缺口：审代码本身，而不是审设计。于是评审拍从"前置拷问"演进为"后置冷读"——这就是 FuseReview。

### 转折 7：闸门该拦的时候拦，该问的时候问

FuseReview 的初版设计是自动闸门：AI 根据任务数、破坏性自动判断要不要评审。这个方案被否决了，理由是：**让 AI 用粗糙启发式做价值判断，是把最容易出错的环节交给最没有信息的角色**。6 个任务可能是 6 个一行修复，3 个任务可能是棘手的并发重写——真正掌握信息的是全程参与变更的人。

最终形态是**人工检查点**：apply 完成后 AI 必须提问（关闭静默跳过），呈现事实（任务数、是否用过 subagent、涉及模块）但不裁决，决定权在人；跳过必须写入收尾报告留痕（跳过从"不可见"变成"可审计"）。

这个模式的适用判据也清晰了：**约束 AI 用铁律（AI 会偷懒），裁决权归人用人检查点（人有上下文）**。流水线上现在有四个人工检查点：Path A 方案确认、逐制品审阅、apply 入口的模型切换节拍、apply 出口的 FuseReview 检查点。

### 转折 8：方法论要能吃自己

SpecFuse 的变更也走 SpecFuse 的流程（dogfooding）。这不是修辞——它产生了真实收益：

- FuseReview 拍的第一次实战，就是在它自己的实施变更上做的冷读评审，抓出了三个测试强度缺陷；
- "移除 Grill"这个变更本身，走完了 Think → Do → FuseReview → Verify → Archive 全程，包括删除型变更的反转 TDD（先写"缺失断言"再删代码）；
- 流水线对"删除流水线的一拍"这种元变更同样有效，说明约束体系没有和任何特定拍硬耦合。

方法论吃自己的代价是慢一点；回报是每次演进都自带完整证据链。

## 三、解决方案：SpecFuse 做了什么

> **设计一条完整的 AI 工作流水线，把设计思考、TDD 实施、冷读评审、验证归档编排成连贯节奏——用户按节奏推进，能力调度和纪律约束在背后自动接管。**

### 方案 1：TDD 铁律——解决"完成声明不可信"

```
IRON LAW: NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE.
```

设计要点：措辞是功能性的（"IRON LAW" 对 AI 的遵守率显著高于 "should"）；要求粘贴原始输出而非回答"通过了吗"（让验证行为可观察）；"fresh" 防止缓存作弊。

### 方案 2：条件触发的 Subagent/Worktree——解决"大变更塌方"

触发条件用 AND 连接（任务多 + 任务独立 + 模块清晰 + 上下文紧张），防止过早触发；同时声明"不需要"的情况，防止过度保守。

### 方案 3：强制设计阶段——解决"方向性错误"

brainstorming 一次一问、2-3 方案对比、Non-goals 强制声明。OpenSpec 的 artifact 依赖链（tasks 依赖 specs，specs 依赖 design，design 依赖 proposal）强制顺序，跳不过去。

### 方案 4：Artifact 链——解决"决策不可追溯"

每个变更自动产出 proposal → design → specs → tasks，归档后沉淀在 `openspec/changes/archive/`。三个月后有人问"为什么这样做"，答案在那里。

### 方案 5：FuseReview——解决"绿但是错"

apply 完成后的冷读评审：

- **基线机制**：apply 启动时记录 HEAD 到变更状态，评审对象精确定义为 `基线..HEAD`。本地一次性写定，零漂移——比 PR 评审反复验证活 base 简单一个量级。
- **冷读**：评审者必须是未参与实现的独立上下文。作者自评自己刚写的代码，认知距离为零，抓不到东西。
- **十一项检查带实质**：测试强度（含"引入回归、看它变红、回滚"的验证配方）、缺失检测、范围吻合、真实入口、接口两侧、七类生命周期缺陷分类学、强制路径、配置选择、能力消费者匹配、借用状态、边界值。检查项知识来自对成熟工程实践的融合提炼。
- **输出纪律**：每条发现含缺陷/位置/影响/证据；阻塞与建议强制分离；机械门禁已覆盖的不重复提。
- **终止条件**：全量评审至多一轮，修复只复审修复 diff——防止评审死循环。

### 方案 6：DESIGN-TOKENS 三道门——解决"UI 项目视觉漂移"

brainstorming 结束时按三道门评估是否生成设计令牌：Gate 1 是否有面向用户的 UI（主触发）→ Gate 2 视觉决策是否已有归属（豁免）→ Gate 3 意图强度校准（强意图直接问卷，弱意图先声明"视觉未在头脑风暴中讨论过"再问卷）。触发判据是"有没有 UI"而不是"用户有没有谈视觉"——WebUI 项目的视觉令牌是必然产物，不取决于话题是否被提起。

### 方案 7：CLAUDE.md 作为流水线调度协议

核心产物是一份调度协议，声明"哪个阶段激活哪些能力、以什么约束强度执行"。调度和能力解耦（上游独立迭代）、项目级策略（不同项目不同松紧）、零侵入可逆（删除 FUSION 块即回到无调度状态）。

## 四、流程设计：四拍流水线

```
Think       /opsx:new 或 /opsx:propose
              ↓  brainstorming：一次一问、方案对比、Non-goals
              ↓  proposal → design → specs → tasks

Do          /opsx:apply
              ↓  模型切换检查点（人工裁决）
              ↓  严格 TDD：失败测试 → 最小实现 → 粘贴证据
              ↓  基线在此拍开始时记录

FuseReview  apply 收尾检查点（人工裁决）
              ↓  呈事实：任务数 / subagent 使用 / 涉及模块
              ↓  同意 → 独立上下文冷读 基线..HEAD，执行 11 项检查
              ↓  blocking 走 TDD 修复，修复只复审修复 diff；跳过必留痕

Verify      /opsx:verify → /opsx:archive
              ↓  spec 逐条对照 + 全量测试 + lint 零警告 → 归档
```

### Think：方案设计与制品生成

两种节奏：Path A（`/opsx:propose`）一次生成全部制品；Path B（`/opsx:new` + `/opsx:continue`）一次一个制品、每步人工确认。涉 UI 项目在 brainstorming 结束时触发 design-md 三道门。

### Do：TDD 实施

每任务红绿循环，完成必须贴新鲜终端证据。subagent 模式下每个 subagent 的产出在合并前过两阶段评审（spec 合规 → FuseReview 技能），大变更另按条件触发 worktree 隔离。

### FuseReview：冷读评审

定位是**对 diff 的语义评审**，补三个既有闸门的盲区：Grill 式的制品审查管不到代码（已移除）、TDD 管不了断言有效性、Verify 的机械对照区分不了"符合 spec"和"实现是对的"。人工检查点决定是否执行——评审的价值 = 评审者与作者的认知距离，而"值不值得这个成本"由掌握全量上下文的人判断。

### Verify：验收归档

全量视角补 Do 的单任务盲区：所有任务加起来是否覆盖 spec 全部要求、有无回归、质量基线是否维持。归档时同步主 specs，变更沉淀为可追溯历史。

### 附录：Grill 的兴衰（诚实的演进记录）

- **加拍**（2026 年中）：实施前拷问设计，理论价值是"缺陷修复成本最低点"。
- **自包含化**（2026-08-05）：审查方法从"依赖宿主文档的薄壳"升级为技能自含，补上数据流完整性维度。
- **作为先例**（2026-08-26）：FuseReview 的自包含原则、阻塞/建议分级、终止条件设计都沿用了 Grill 的既有机制。
- **移除**（2026-08-27）：用户裁决"流程太重"。彻底删除：模板、分发、协议段落、5 个能力的主 specs。存量项目重装时技能文件保留（脚手架只加不删），退化为纯手动技能。

删掉一个拍不是失败——它证明流水线的拍是**可证伪的**：每一拍都要用增量价值为自己续租。Grill 留下的概念（阻塞分级、证据纪律、自包含技能）活在 FuseReview 里。

## 五、设计决策的代价与局限

### 代价 1：声明式约束没有系统级保障

CLAUDE.md 是纯文本，AI 在极端条件下可能违反。这是架构选择的根本代价。缓解：等 hook API 成熟后增加运行时验证层；当前用"粘贴证据"和检查点提问作低成本替代。

### 代价 2：小变更的固定开销

artifact 链对 5 分钟能解决的变更是过度的。缓解方向：quick-fix 路径仍在路线图上。FuseReview 的人工检查点设计部分吸收了此教训——固定成本能砍就砍，砍不掉的交给人的裁决。

### 代价 3：人工检查点依赖人的诚实

跳过留痕解决了"不可见跳过"，但人在时间压力下仍会说"不"。这与 Grill 时代"强制的负担"是同一枚硬币的两面：强制产生规避冲动，自愿产生惰性跳过。当前选择接受后者——因为留痕让它可审计，而强制的规避是不可审计的。

### 代价 4：仅支持 Claude Code

融合规则的表达方式（CLAUDE.md + 技能激活）目前只有 Claude Code 原生支持。多平台适配不是格式转换，是理解每个平台对"行为约束"的支持深度。

### 代价 5：评审发现的质量决定评审的价值

FuseReview 的成本失控点从来不是读取，而是弱发现引发的浪费修复。输出纪律（证据强制、阻塞建议分离）是成本上限装置。首版检查项全量上线，基于真实使用数据再缩减——这是明确记录的后续意图。

## 六、核心信念

回到最初的问题：SpecFuse 在赌什么？

赌的是：**在 AI 能力快速进步但可预测性尚未跟上的窗口期，结构化的流程约束是工程产出可靠性的必要条件。**

这个赌注的期限是有限的。当 AI 的行为可预测性足够成熟，"提前声明规则然后希望 AI 遵守"的范式可能让位给更轻量的"行为监控 + 实时纠正"。

但在那之前，SpecFuse 选择保守的一边：流程成本是已知的、线性的、可控的；纪律缺失是未知的、非线性的、不可控的。

第二版新增的信念来自两次实战：**流水线的每一拍都应该能被它自己审查、被它自己移除。** Grill 的移除不是流水线的损失，是流水线成熟度的证明——一个不敢删自己组件的方法论，大概也不配要求别人遵守它的纪律。

工程的核心从来不是追求最优解，而是控制下行风险。SpecFuse 选了控制风险那一边——包括控制"流程本身变成风险"的下行风险。

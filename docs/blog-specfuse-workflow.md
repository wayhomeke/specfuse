# AI 开发流水线实战：Think → Do → FuseReview → Verify

> 这是 SpecFuse 工作流文章的第二版（第一版 [2026-06-26](./blog-specfuse-workflow-2026-06-26.md)）。变化的地方：流水线从 Think → **Grill** → Do → Verify 演进为 Think → Do → **FuseReview** → Verify——实施前的设计拷问（Grill）被移除了，替换为实施后的冷读评审（FuseReview）。为什么改、改完什么样，这篇文章讲清楚。

---

## 工具够多了，流程在哪？

用 AI 写代码，你手里的工具越来越多——openspec、superpowers、speckit、各种 review 插件——各有所长又互相覆盖。

每个工具都能让你完成一次 vibe coding，但痛点在于逻辑上如何协作：你有搅拌机、烤箱、模具——但没有食谱。没人规定"先搅拌再入模再烘烤"的顺序，出来的东西全凭手感。

SpecFuse 做的事没变：**不发明新工具，给已有工具编排一条流水线。** OpenSpec 提供流程脚手架，Superpowers 负责需求对齐和 TDD 铁律，编排层决定它们在什么时刻以什么强度激活。

变了的是拍序。先说结论，再说为什么。

---

## 四拍流水线：Think → Do → FuseReview → Verify

```
Think       /opsx:new 或 /opsx:propose
              ↓  brainstorming：一次一问、2-3 方案对比、Non-goals
              ↓  proposal → design → specs → tasks

Do          /opsx:apply
              ↓  严格 TDD：失败测试 → 最小实现 → 粘贴终端证据
              ↓  开始时记录基线 commit（评审对象的起点）

FuseReview  apply 收尾检查点
              ↓  AI 必须问你：要不要评审？（呈事实，不替你决定）
              ↓  同意 → 独立上下文冷读全部改动，出发现清单
              ↓  blocking 走 TDD 修复；跳过则留痕记录

Verify      /opsx:verify → /opsx:archive
              ↓  spec 逐条对照 + 全量测试 + lint 零警告 → 归档
```

关键体验还是那个：每拍你只敲一个命令，背后的能力调度对你透明。不需要记"现在该激活哪个插件"，流水线替你记。

---

## Brainstorm：不是让 AI 自嗨，是双向对齐

这部分没变，因为它一直是对的。

很多人把 brainstorm 理解成"让 AI 帮我想方案"，然后一路 yes——AI 提方案你说行，AI 展开细节你说行，最后生成一堆制品，你其实都没仔细看。这样和直接让 AI 一次性生成所有文档没区别。

brainstorm 真正的价值是双向对齐：

- **AI → 人**：AI 提出技术方案，你追问细节理解它的逻辑。这是知识传递。
- **人 → AI**：你抛真实业务场景，让 AI 重新判断哪个方案更合理。这是场景校准——AI 不知道你的用户怎么用、你的系统有什么历史包袱。

形式上就是项目评审会，只是评审对象从"人写的文档"变成"AI 生成的方案"。频率从双周一次变成每个变更都有，问题暴露时机从"半个月后的评审会"提前到"动手之前的十分钟对话"。

---

## TDD 铁律：在 AI 场景下意义变了

这部分也没变。

TDD 在传统开发中的核心价值是驱动设计。在 AI 编码场景下，它的核心价值变成：**提供可验证的完成证据。**

AI 说"这个任务完成了"——你信吗？它声称跑过测试了——你怎么验证？

答案是要求它粘贴终端原始输出。不接受"我认为它能工作"，不接受"逻辑上没问题"，只接受"这是我刚跑的测试输出，全部绿"。写失败测试 → 最小实现 → 粘贴证据 → 才能标完成。测试是可选的话，AI 在上下文压力大时会跳过验证——这是观察到的实际行为，不是猜测。

---

## 那 Grill 去哪了？

第一版文章里，Think 和 Do 之间有 Grill：制品生成完毕后，AI 反过来质问你的设计，在写代码之前堵设计缺陷。

它被移除了。原因很朴素：**流程太重**。

一问一答的审查协议、备份回滚、9 问循环、一致性扫描——对大变更有价值，但多数变更用不上，性价比不高。而且它要抓的问题（方向错误、边界不清）大部分已经被 brainstorm 的方案对比和逐制品审阅覆盖了，独特增量小于固定成本。

这个决策本身也是走流水线做的：提案、辩论（降级为可选检查点还是彻底移除）、彻底移除、归档。一个方法论敢删掉自己的环节，说明它的环节不是图腾，是可以被增量价值证伪的设计。

但 Grill 留下的东西没浪费——它的阻塞/建议分级、证据纪律、自包含技能形态，全部活在继任者 FuseReview 里。

## FuseReview：质检从出厂前移到出厂后

Grill 的位置是"实施前审设计"。但实践中暴露了一个更隐蔽的问题，是实施前审查永远抓不到的：

**测试存在且全绿，不代表测试证明了任何东西。**

断言可以复述实现、可以永真、可以只测外壳。TDD 铁律保证了"测试存在且通过"，但保证不了"测试在目标回归上真的会失败"。这类"绿但是错"的代码能通过所有既有闸门——因为所有闸门都信任绿色测试。

FuseReview 就是为此设计的，几个关键机制：

**① 人工检查点，不是自动闸门。** apply 完成后 AI 必须问你要不要评审——问题不能跳过，但答案由你定。呈现的是事实（任务数、是否用过并行实施、涉及哪些模块），不做"大变更就审、小变更不审"的自动判断。为什么？因为 6 个任务可能是 6 个一行修复，3 个任务可能是棘手的并发重写——**真正掌握信息的是全程参与的你，不是任何启发式规则**。跳过也可以，但必须写进收尾报告留痕：跳过从"不可见"变成"可审计"。

**② 冷读。** 评审者必须是没参与实现的独立上下文。作者自评自己刚写的代码，认知距离为零，抓不到东西。评审对象也定义得精确：apply 开始时记录一个基线 commit，评审范围就是 `基线..HEAD`，没有 PR 评审那种 base 漂移的麻烦。

**③ 带实质的检查项。** 不是"看看代码质量"的泛泛而谈：测试强度（含"故意引入回归、看测试变红、回滚"的验证配方）、缺失检测（该有而没有的文档/测试/清理逻辑）、范围吻合（每段新代码映射到哪个 spec 条目）、真实入口（测试走的是发布路径还是手工装配）、接口两侧、七类生命周期缺陷模式……每条检查自带判据，不依赖评审者的个人发挥。

**④ 有牙齿的终止条件。** blocking 发现必须先写"能抓住它的失败测试"再修；修完只复审修复的部分，不触发第二轮全量评审——防止评审变成无底洞。

## 场景叙事：一次真实的 FuseReview 长什么样

用 SpecFuse 自己的变更举例（这条流水线吃自己的狗粮）。变更内容：给流水线新增 FuseReview 这一拍，13 个任务。

实施按 TDD 走完，717 个测试全绿。apply 收尾，检查点弹出：

> 变更事实：13 个任务，单代理实施，涉及 3 个模板模块 + 脚手架 + 6 个测试文件。是否进入 FuseReview？

选择进入。一个没参与实现的独立上下文被派发出去，冷读全部改动。几分钟后回来一份清单：

```
Blocking（3 项，全部 [test-strength]）：
- skip-trace 测试的两个断言词在输出里有其他出处——删掉整段留痕要求，测试照样绿
- "禁止静默推进"只断言了 "silent" 一个词——改成 "is acceptable" 也不翻红
- 七类缺陷模式的 token 断言没限定段落——删掉其中两类，断言仍绿

Suggestion（4 项，记录不强制）
```

三条全是同一族：**断言在合理回归下不会失败的测试，是假守卫**。机械门禁（全绿）对这类缺陷天然失明——这正是 FuseReview 存在的理由。

修复按规矩走：断言改成段落独有措辞、按段切片限定。然后做了验证守卫的验证——故意引入三个变异（删段落、弱化措辞、删缺陷类），跑测试，**恰好三个加固断言翻红**，无多杀无漏杀，回滚变异，全量测试恢复绿。

同一评审者复审修复部分：三项全部关闭，无新增问题。评审收敛，进入 Verify。

| 环节 | 没有它会怎样 |
|------|-------------|
| Brainstorm | 直接开写，"自动闸门还是人工检查点"的取舍没人挑战过 |
| TDD | 13 个任务的证据链缺失，完成声明不可信 |
| FuseReview | 三个假守卫混进主干，日后"测试绿了"继续骗人 |
| Verify | 不知道实现和 spec 逐条对上了没有 |

## 编排的意义：为什么不是"装三个插件"

这部分还是那个逻辑：**谁来记住"现在该激活什么"？**

你来记——你会忘。尤其第三个小需求的时候，你会想"这个太简单了不需要 brainstorm"，然后写到一半发现方向错了。

流水线来记——每个命令背后自动调度对应的能力。调用"开始实施"，TDD 铁律自动生效；实施完成，评审检查点自动弹出。技术上通过声明式规则实现：绝对不可违反的（证据铁律）标 MUST，需要人裁决的（是否评审）设为检查点提问。

这版新增的体感是：**检查点是比强制更成熟的约束形态。** 强制引发规避冲动，自愿伴随惰性跳过——但前者不可审计，后者留痕。把 AI 会偷懒的环节做成铁律，把需要上下文判断的环节交还给人，各归各位。

---

## 流程思考：门槛没有降低

这套流程不会降低对开发者的能力要求。说直接点，它对架构认知和系统理解力的门槛比"纯手写"还高。

brainstorm 阶段 AI 给你三个方案，你得能判断哪个在你的业务场景下更合理。FuseReview 检查点弹出时，你得根据变更的真实风险决定审不审。评审报告回来后，你得看得懂"这个断言为什么是假守卫"。

每一个环节，AI 都在问你问题。但如果你对系统没有整体认知，你连问题本身都没法正确回答。

传统工具降低执行成本，这套流程降低决策摩擦——决策频率越高，对决策者的认知水平要求越高，不是越低。我的判断不变：AI 工作流最终会拉大"能做架构决策的人"和"只能执行既定方案的人"之间的差距。

## 试试看

```bash
cd your-project && npm create specfuse@latest
```

一条命令把整条流水线注入项目：brainstorming、TDD 铁律、FuseReview 检查点、artifact 管理，开箱可用。15 个内置技术栈，自定义栈一份 YAML 搞定。

不想装工具也没关系。这篇文章的核心观点在方法论层面：**AI 编码需要的不是更多工具，而是一条把工具编排成连贯节奏的流水线**——以及一个敢删掉自己环节的方法论。

# SpecFuse Project Initialization

Initialise the current directory with the SpecFuse fusion methodology: a
**Think → Do → FuseReview → FuseQA → Verify** pipeline, built on OpenSpec as the
flow engine and Superpowers for behavioural discipline.

You are the agent executing this skill. This file does not hand you content to
copy — this repository is cloned next to you, and the canonical text lives in it.
What this file tells you is **where that text is** and **what has to be
translated** for the agent you are. How you materialise the result is your call,
made against your own platform's conventions.

## When to Use

- The user wants a project set up with the SpecFuse methodology
- The user says "init specfuse", "setup specfuse", or "set up spec-driven development"
- A project directory exists but lacks an instruction file and `openspec/` configuration

## When NOT to Use

- The project already has an instruction file carrying `<!-- FUSION:START -->`
- The user only wants to explore or brainstorm an idea

## What gets produced

| Target | Canonical source |
|---|---|
| the project's instruction file | `composeCLAUDEmd()` in `src/templates/claude-md.ts` |
| `.gitignore` | `composeGitignore()` in `src/templates/gitignore.ts` |
| the agent's settings / permissions file | `composeClaudeSettings()` in `src/templates/claude-settings.ts` |
| `openspec/config.yaml` | `composeOpenspecConfig()` in `src/templates/openspec-config.ts` |
| the three skill definitions | `composeDesignMdSkill()` in `src/templates/design-md-skill.ts`, `composeFuseReviewSkill()` in `src/templates/fusereview-skill.ts`, `composeFuseQASkill()` in `src/templates/fuseqa-skill.ts` |
| the template packs two of those skills carry | all of `src/design-md/templates/` and `src/fuseqa/templates/` |
| the `/opsx:*` command surface | generated by OpenSpec itself — see Step 4 |

**The skill definitions are not optional.** The instruction file you generate
names them — it says the review method lives in `.claude/skills/fusereview/SKILL.md`
and the end-to-end method in `.claude/skills/fuseqa/SKILL.md`. Omit them and the
project ships with an instruction file pointing at files that were never
written, which disables two of the five beats. Scaffold them alongside
everything else, and carry their template packs whole.

## Step 1: Detect existing state

```bash
test -f AGENTS.md && echo "instruction file exists" || echo "no AGENTS.md"
test -f CLAUDE.md && echo "CLAUDE.md exists" || echo "no CLAUDE.md"
test -d openspec && echo "openspec/ exists" || echo "no openspec/"
test -d .git && echo "in a git repo" || echo "not a git repo"
```

If the existing instruction file already carries `<!-- FUSION:START -->`, tell the
user and ask before replacing anything — see *Merging* below.

## Step 2: Ask the two questions

Two questions, matching what the CLI asks. There is no third:

1. **Initialise a git repository?** Ask this **only when you are initialising a
   new project directory**. When the directory already exists, do not ask and do
   not create one — the CLI behaves the same way.
2. **Initialise OpenSpec?** Ask this either way. OpenSpec supplies the command
   surface the pipeline is entered through.

Do **not** ask which language, framework, or toolchain the project uses. SpecFuse
is a process, not a selector: the project's own files declare its build, test and
lint commands, and the instruction file you generate says "the project's test
command" rather than naming one.

## Step 3: Generate the files

### 3a. Read the canonical sources

Read each source named in the table above and reproduce **what it returns**. The
composers are pure functions — deterministic string assembly, no inputs beyond
the ones you can see.

**The text you are reading is written in Claude Code's dialect.** Do not copy it
verbatim. It names files, directories, tools and commands that belong to that
platform; the next section is the list of what to change.

### 3b. Translate the platform-specific surfaces

| In the canonical text | What it is | Say instead |
|---|---|---|
| `CLAUDE.md` | the instruction file's name | **your** platform's instruction file — `AGENTS.md`, `.cursor/rules/`, `.github/copilot-instructions.md`, `GEMINI.md`, or whatever yours reads |
| `.claude/skills/` | where skill definitions live | your platform's equivalent, or inline them into the instruction file if it has no skill mechanism |
| `/opsx:*` | the command surface | your platform's rendering of it — obtain it via `openspec init --help`, which lists the tool ids OpenSpec can render for |
| `AskUserQuestion` | the user-question tool | your platform's way of asking the user something, or a plain prose question if there is none |
| `.claude/settings.local.json` | the permission config | your platform's permission config, or omit it if your platform has none |

`<!-- FUSION:START -->` and `<!-- FUSION:END -->` stay exactly as they are: they
are plain HTML comments, meaningful to the merge step below and portable as-is.

### 3c. Degrade only what your platform actually lacks

Two of this methodology's dependencies are multi-platform, so check before
degrading:

- **OpenSpec** — run `openspec init --help`. It enumerates the tools it can
  render for. If yours is listed, the command surface works as-is. If not, skip
  the command surface and carry the workflow in the instruction file instead.
- **Superpowers** — if it is available to you (plugin, skill pack, or rules —
  the form varies), use it as named in the canonical text. It carries its own
  per-platform mappings, including for tool names, so no translation is needed
  there.

Nothing in this methodology is unavailable merely because you are not Claude
Code. In particular the subagent and git-worktree instructions come **from
Superpowers**, not from this project — so they are covered by the Superpowers
check above and must not be degraded on their own.

If Superpowers is genuinely not available to you, execute the disciplines
directly rather than dropping them. Each reduces to one requirement:

- where the text says to activate `brainstorming` — reach agreement on the approach before building, and ask one question at a time
- where it says `test-driven-development` — write the failing test first, then the least code that passes it
- where it says `verification-before-completion` — no claim of completion without pasting fresh output as evidence

### 3d. The two nearly-portable files

`.gitignore` is portable as-is: reproduce `composeGitignore()` unchanged. It holds
shared patterns only — IDE, OS, environment, logs, temporary files — because this
project does not presume a toolchain.

`openspec/config.yaml` needs **one substitution**. Its `context` field reads "The
project's own `CLAUDE.md` declares its build/test/lint commands" — apply the same
instruction-file change as 3b, so the config points at the file you actually
wrote. Its `schema` and `rules` sections are portable as they stand.

Create the OpenSpec directory structure:

```bash
mkdir -p openspec/specs openspec/changes/archive
```

### 3e. Merging into a project that already has files

Reproduce the CLI's conservative behaviour, which is defined in
`mergeFusionIntoCLAUDEmd`, `mergeGitignore` and `mergeClaudeSettings` in
`src/scaffolder.ts`. Read them; in outline:

- **Instruction file** — replace only the text between `<!-- FUSION:START -->` and
  `<!-- FUSION:END -->`. Everything the user wrote outside those markers survives
  untouched. If there are no markers, append.
- **`.gitignore`** — append only the patterns that are missing. Never remove a
  line the user has, even one this project would not have written.
- **Settings / permissions** — merge, de-duplicating; do not replace.
- **`openspec/config.yaml`** — leave an existing one alone.

Never overwrite a skill definition the user has authored.

## Step 4: Initialise OpenSpec, and report the outcome

Obtain your tool id from `openspec init --help`, then:

```bash
openspec init --tools <your-tool-id> --force
```

**Distinguish the two ways this can go wrong, because they need different
handling:**

- **The user declined OpenSpec.** Print the `/opsx:*` line unannotated. Nothing
  was attempted, so nothing failed, and there is nothing to report.
- **The attempt failed** — the CLI is absent, or the command errored. Annotate
  that line with a marker pointing at a notice below it, and emit the notice: say
  which piece is missing, say that the `/opsx:*` commands are therefore not
  available and the pipeline cannot be entered until it is fixed, and give the
  commands that repair it. If the CLI itself is missing, that includes installing
  it; if only the init step failed, do not tell the user to install it again.

The failure path must not present `/opsx:propose` as a working next step. A
summary that promises a command that does not exist is worse than one that
reports the gap.

## Step 5: Summary

Tell the user what was created and what to do next. Keep "next steps" honest: if
OpenSpec is ready, `/opsx:propose`, `/opsx:new` and `/opsx:explore` are the ways
in; if it is not, say so and point at the repair instead.

## Why this file has no inlined methodology

It used to copy the pipeline text into itself. That copy went four months without
an update and lost three of the five beats, because nothing connected it to the
source. Pointing at `composeCLAUDEmd()` instead means there is no copy to drift —
the only thing that can go stale is a pointer, and a test in this repository
fails when one does.

## Why

When the OpenSpec CLI cannot be installed, scaffolding reports success and tells the user to run a command that does not exist. Reproduced against the built artifact with `npm` stubbed to fail and `openspec` off `PATH`:

- exit code **0**, spinner reads `Project scaffolded!`
- `Next steps` ends with `/opsx:propose   # start your first change`
- `.claude/commands/opsx/` is absent — all 11 slash commands are generated by `openspec init`, so none exist
- the `spinner.warn` about the failure is pushed out of view by 8 further lines of output

Without `/opsx:*` the entire generated protocol is unreachable: Path A/B, the apply-exit checkpoints, the five-beat pipeline are all entered through those commands. The user is left with a `CLAUDE.md` nothing can trigger, and the one line of output that would have explained it is the easiest to miss.

## What Changes

OpenSpec stays **optional** — a failed install must not abort scaffolding or change its exit code. The defect is visibility, not policy.

- `src/scaffolder.ts`: track whether OpenSpec ended up ready in a local variable. The three failure branches currently call `spinner.warn` and discard the outcome, so the print block below cannot know what happened.
- Annotate the one line that is wrong: when OpenSpec is not ready, `/opsx:propose` prints with a trailing marker pointing at the notice below instead of `# start your first change`. The `Next steps` block keeps its structure and every other line verbatim.
- Append an end-of-output notice block when OpenSpec is not ready, in the same shape as the existing Superpowers notice: what is missing, why it matters, and the two commands that fix it (`npm i -g @fission-ai/openspec`, then `openspec init --tools claude --force`).
- Distinguish the two failure modes in that notice: **install failed** (needs both commands) vs **install succeeded but `openspec init` failed** (needs only the init command). Currently both produce differently-worded `spinner.warn` calls that scroll away; the persistent notice must not lose that distinction.

## Non-goals

- **Not making OpenSpec required.** No non-zero exit, no `process.exit`, no abort. A user who only wants `CLAUDE.md` plus the skill files still gets a successful scaffold.
- **Not adding a `--no-openspec` flag.** Declining OpenSpec is already possible interactively; the prompt exists.
- **Not restructuring `Next steps`.** No reordering, no conditional block, no inserted install lines. One line gains a marker; nothing else moves.
- **Not touching the Superpowers notice.** Superpowers being absent degrades brainstorming quality but leaves `/opsx:propose` working, so its `Next steps` line is not wrong. Merging the two would flatten a real difference in severity.
- **Not retrying the install** or attempting alternative install paths (npx, local install).
- **Not changing `spinner.warn` behavior during the run.** The transient warnings stay; the notice is additive.

## Trade-offs

**Alternative 1 — replace `Next steps` with a repair sequence when OpenSpec is missing.** Rejected by explicit decision: it makes the failure path structurally different from the success path, and the user asked for the Superpowers treatment — a suggestion at the end, not a rewritten flow.

**Alternative 2 — treat a failed OpenSpec install as fatal (non-zero exit).** Rejected: OpenSpec is documented as optional, and a hard failure would block users who want only the methodology files. It would also turn a recoverable situation into a CI failure with no way to opt out short of a new flag.

**Alternative 3 — append the notice but leave `/opsx:propose` unannotated.** Rejected: the notice is the part most likely to be skipped — that is precisely how the current `spinner.warn` gets lost. A user who reads only `Next steps` would still be sent to a command that does not exist. The marker is what connects the two.

## Capabilities

### New Capabilities

- `openspec-readiness-reporting` — the scaffolder's contract for reporting OpenSpec readiness: scaffolding succeeds regardless, the `/opsx:propose` line is annotated when OpenSpec is not ready, an end-of-output notice states the missing piece and its repair commands, the notice distinguishes install failure from init failure, and neither the exit code nor the rest of `Next steps` changes.

### Modified Capabilities

None. `scaffold-tool-boundary` governs what scaffolding must NOT do (no CodeGraph, no stack); OpenSpec readiness reporting is new surface, not a revision of those requirements.

## Impact

**Modified:** `src/scaffolder.ts` — capture OpenSpec readiness (ready / install-failed / init-failed) in the existing `config.initOpenspec` block, annotate one `Next steps` line, append the notice block.

**Tests:** `tests/scaffolder.test.ts` — assert the annotation and notice appear when OpenSpec is unavailable and are absent when it is ready; assert the exit path is unaffected. `tests/e2e/scaffold-tool-boundary/` — the existing E2E cases already run with `openspec` off `PATH` and a stub `npm` that exits 1, so they scaffold through exactly this failure path and can assert the real stdout of the built artifact.

**User-visible:** unchanged output when OpenSpec is ready; one annotated line plus a trailing notice when it is not. Exit code stays 0 in both cases.

## Verification strategy

- `npx vitest run` — full suite green, including the E2E cases that already exercise the OpenSpec-absent path.
- `npx tsc --noEmit` — clean.
- End-to-end against the built artifact in a scratch `HOME` with `openspec` off `PATH` and `npm` stubbed to exit 1: assert exit code 0, assert stdout contains the annotation and the notice with both repair commands, assert `.claude/commands/opsx/` is absent (the condition being reported).
- Positive control with OpenSpec reachable: assert stdout contains neither the annotation nor the notice, and that `/opsx:propose   # start your first change` prints verbatim.
- `grep` the print block to confirm `Next steps` retains its original lines.

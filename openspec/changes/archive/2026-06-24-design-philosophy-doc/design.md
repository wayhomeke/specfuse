## Context

SpecFuse 项目当前有两类文档：面向用户的 README.md（使用指南）和面向评估者的 `docs/product-overview.md`（功能介绍 + 市场定位）。两者都回答"是什么"和"怎么用"，但不回答"为什么这样设计"。

项目已积累 46 个 commits 的设计决策（三阶段流水线、声明式触发、CLAUDE.md 桥接、渐进式复杂度等），这些决策的推导过程仅存在于开发者头脑中。本次变更产出一份深度设计手记，将隐性知识显性化。

**约束条件：**
- 纯文档产出，无代码变更
- 与 product-overview.md 互补不重叠
- 目标篇幅 8000-12000 字
- 专业叙事风格，第三人称，论点需有思辨性
- 关键决策点需引用实际的 CLAUDE.md 模板代码片段

## Goals / Non-Goals

**Goals:**
- 产出 `docs/design-philosophy.md`，六章线性叙事结构
- 每个设计决策呈现为"问题 → 正反论证 → 结论 → 代价"的完整链路
- 分层表达：主文面向所有技术读者，代码片段面向工程师
- 从项目实际代码（`src/templates/claude-md.ts`、CLAUDE.md 模板输出）中提取真实示例

**Non-Goals:**
- 不重新设计或修改任何现有功能
- 不产出英文版本（当前只需中文）
- 不包含性能基准测试或量化数据（product-overview 已有）

## Decisions

### 1. 文档位置：`docs/design-philosophy.md`

独立文件而非扩展现有文档。

**理由：** product-overview.md 的目标是快速传达"SpecFuse 是什么、能做什么"（信息密度优先）。设计手记的目标是深入展开"为什么这样做"（思辨深度优先）。混合两种目标会稀释两者的效果。

### 2. 六章线性结构

```
第一章：核心问题定义（能力 vs 纪律的矛盾）
第二章：两个工具的局限与融合动机
第三章：三阶段流水线设计（Think-Do-Verify）
第四章：AI 行为建模与约束哲学
第五章：已知局限与诚实反思
第六章：核心信念收束
```

**理由：** 线性叙事匹配"决策链路"的表达需求——每一章的结论是下一章的前提。读者跟随认知路径前进，而非在独立章节间跳转。

**被否方案：** ADR（Architecture Decision Records）格式——每个决策独立成文件，缺乏叙事连贯性，适合团队内部归档但不适合对外传播。

### 3. 内容来源策略

从三个来源提取设计决策的素材：
- **`src/templates/claude-md.ts`**：实际的约束声明生成代码，提取 CLAUDE.md 输出片段
- **`docs/product-overview.md`**：已有的决策描述（如"为什么 CLAUDE.md 作为桥接层"），转化为思辨性论证
- **commit history + openspec archive**：设计演进轨迹

**理由：** 确保文档基于事实而非回忆，所有论点可溯源到代码实现。

### 4. 写作风格约定

- 第三人称专业口吻（"SpecFuse 的设计选择是..."而非"我们决定..."）
- 决策框用 blockquote 呈现被否方案和选择理由
- 代码片段限定在展示"方法论如何编码为机器指令"的场景

**理由：** 目标读者兼含外部技术决策者和社区读者，过于内部化的口吻会降低可信度。

## Risks / Trade-offs

- **[内容与代码脱节]** 文档引用的代码片段可能随版本更新而过时 → 缓解：引用时标注版本（v0.2.0），并在文档头部声明快照时间
- **[篇幅失控]** 8000-12000 字目标在展开六个主题时可能不够或溢出 → 缓解：第一/六章控制在 1000-1500 字，第三/四章各 2500 字，第二/五章各 1500 字
- **[与 product-overview 内容重叠]** 部分决策（如"为什么融合"）在两处都有提及 → 缓解：design-philosophy 从思辨角度展开（正反论证），product-overview 保持结论性陈述，引导读者互相参照

```
└── design-philosophy.md     (NEW — 设计哲学/决策推导)
```
